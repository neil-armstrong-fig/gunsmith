# AGENTS.md: api

The Cloudflare Worker: one Worker serves the site (static assets) and `/api/*` from the same origin, so there is no CORS and the
session cookie will be same-site. Root `AGENTS.md` still applies. The design is `docs/match-netcode.md` (rooms, the tick, fog) and
`docs/ai-hosting.md` (the AI pipeline runs inside this Worker). Modelled on janggi's `api/`.

## Import boundaries

`api/` may import `@gunsmith/shared`, `@gunsmith/engine` and `@gunsmith/ai` (`eslint.config.js`). **Nothing imports it**: the webapp
and the acceptance specs reach it over HTTP and WebSocket, so a frame's shape is written out on both sides (`webapp/src/online/types/`).
Import with the `@src/*` alias.

## What is here

- `ApiWorker.ts` is the runtime's front door and, with `durable-objects/match/Match.ts`, the only code that touches the Workers runtime. Keep them to wiring: they are not unit tested.
- **`router/` is the front door's dispatch, one folder per route (2026-11-19).** `router/HandleApiRequest.ts` only matches the path and hands the request to the route that owns it, in `router/routes/<name>/`: `rooms/` (`POST /api/rooms`, a friend code), `socket/` (a WebSocket upgrade on `/api/rooms/<code>/socket`, handed to that room's `Match` Durable Object), `weapons/` and `arenas/` (the generation routes, below), and `shared/` for what two routes use (`ReserveCredit` with its `account-id/`, `prompt-request/` and `types/`; `friend-code/`; the test-only `fake-ledgers/`). A new route is a new folder beside these with its own handler, `types/`, tests and (if it has them) `property-tests/`, plus one branch in `HandleApiRequest.ts`; a helper two routes need goes in `shared/`, one route's helper beneath that route. `router/types/GenerationPipelines` is the pipelines the Worker hands the router. The Durable Objects are not routes and live in `durable-objects/` (next bullet).
- **`durable-objects/` holds the three Durable Object domains (2026-11-19):** `match/` (a room's match), `credit-ledger/` (one `CreditLedger` per account) and `spend-ledger/` (the one global `SpendLedger`), each a folder with its one wiring root file, the plain classes beneath it and its tests; `shared/utc/` is what the two ledgers share. `ApiWorker.ts` exports them (`wrangler.jsonc` names the classes) and no route imports them: a route reaches one through the `env` namespace (`MATCHES`, `CREDITS`, `SPEND`), so renaming a class or folder never touches a route. A new Durable Object is a new folder beside these.
- `durable-objects/match/room/MatchRoom.ts` is the match as plain state, no network: seats, what each seat last asked for, the engine's world, the tick. `match/Match.ts` only feeds it frames and a clock and sends what it answers. `match/messages/` parses what a client sends (`unknown` until parsed; the engine then caps what an input may ask for): an `input` frame (`ParseInputMessage`) or a `ready` frame (`ParseReadyMessage`).
- **Rounds and the match are the room's.** A room's world carries a best of three (`startMatch`), which `playStep` scores as each round ends. A decided round freezes until **both seats send `ready`**; then `MatchRoom` begins the next round (`nextRound`: the score kept, both fighters restored to their starting places) or, once the match is decided, a fresh match. A `ready` while the round is still being fought is ignored, so a seat cannot ask ahead. Each snapshot also carries `ready {player, opponent}` (who has asked, from that seat's side); it is only flags, so it tells nothing about where anyone is. There is no ring and no pickup in a room yet.
- **A seat is kept for its person (reconnect, 2026-11-18).** Each seat is given a secret `token` in the `joined` frame (sent once on **every** connection); a browser shows it as `?token=` on the socket URL to get the same seat back (`MatchRoom.reconnect`). Before the match begins a seat that leaves is simply given back (its token is void); after it, `leave` freezes the fighter (its ask is zeroed; it stays in the world and hittable) and the seat waits for the reconnect window (below). A token that is not a seat's is an ordinary newcomer's: with both seats held the socket is closed `4409 room-full`. If the seat's old connection is still open when the token arrives it is closed `4410 replaced`. Both codes mean "do not come back" to the browser. Rebinding **forgets what the seat had reached** (`ack`, its held input): a returning page counts its inputs from zero again, and an old `ack` would make the server drop every one of them as stale. `Match` ignores frames and closes from a socket that no longer holds the seat, so a late `close` cannot freeze the seat's new connection. If both players are away the Durable Object may be evicted and the room's state lost (a known limit).
- **The room does not wait for ever (2026-11-18).** Each seat has a clock of how long it has been silent, counted in the game time `MatchRoom.tick` plays (no wall clock in `MatchRoom`), and checked **one step at a time** so that of two seats running out in one stretch the first is the one that forfeits. It restarts when the seat's person leaves or comes back, **asks for something new** (`forfeit/AskChanged`: the browser's own rule, so the heartbeat repeating the same ask does not count), clicks "Next round", and for both seats when a round is decided or begins. A seat whose person is away may be silent 30 s (`reconnectSeconds`), one who is there 60 s (`idleSeconds`; `DefaultForfeitLimits`). Then it **forfeits**: a round being fought goes to the other seat (`forfeit/ForfeitRound`, scored with the engine's `scoreRound`, so two forfeits lose the match as two lost rounds do); a decided round that was waiting for this seat to click has the _next_ round forfeited as it begins, leaving the other seat the usual "Next round"; a decided match forfeits nothing. **Both seats running out together forfeit nothing** (two people gone is a stall, not a win). The clock stops with the last connection (`Match` clears its interval), so a room everyone has left does not run down. Specs shorten the limits with `?reconnectSeconds=` and `?idleSeconds=` on the page address: the webapp passes them on the socket URL, `Match` reads them from the room's **first** connection only (`forfeit-limits/ParseForfeitLimits`: never longer than the real limits, never under a second, non-numbers ignored).
- **`routes/weapons/` and `routes/arenas/` are the two generation routes (weapon 2026-11-18, arena 2026-11-19).** `POST /api/weapons` (`weapons/GenerateWeaponRoute`) and `POST /api/arenas` (`arenas/GenerateArenaRoute`) take `{prompt}` and an `X-Account-Id` header (`routes/shared/account-id/ParseAccountId`: **a stand-in for the session**, it proves nobody and only names the `CreditLedger`; it goes when sign-in lands). The guards are shared (`routes/shared/ReserveCredit`), in order, each taking nothing: method (405), a pipeline to run (503 `ai-unavailable`), account (401), body (`routes/shared/prompt-request/ParsePromptRequest`, 400), `SPEND.status()` (503 `ai-off` with `returnsAt`), then `CREDITS.reserve(key, kind)` (402 `no-credits`) **before** the pipeline runs and, when the route passes an estimate (`reservedMicrodollars`: the weapon route, `WEAPON_SPEND`), `SPEND.reserve(key, reservedMicrodollars)` after it (credit first, so an account with none never touches the one global ledger; a `paused` spend refunds the credit and answers 503 `ai-off` with `returnsAt`; the arena route passes none yet, so it reserves no spend); the key is a fresh `crypto.randomUUID()` per request. Each route then runs its pipeline and settles. **Weapon:** `created` settles `weapon` (1 credit), `rejected` settles `rejected` (half), `invalid` or a throw refunds; the spend settles at the model calls the outcome made (`durable-objects/spend-ledger/estimate/SettledWeaponSpend`), or in full on a throw (its calls may have been billed). **Arena:** `created` settles `arena` (1), `rejected` settles `rejected` (half), `builtIn` (the model's arena was unusable, so a built-in one is given) **refunds and still answers the arena** (`{status: "builtIn", arena, reason}`), and a throw refunds; a throw is a 502 `generation-failed` on both. A route is handed its pipeline (`WeaponSmith`, `ArenaSmith`, `types/`: `@gunsmith/ai`'s `generateWeapon` / `generateArena` with their models once the Worker has them) through `router/types/GenerationPipelines`: `ApiWorker.ts` passes none, so both answer `ai-unavailable` (no production adapter, no spend). **No production smith may be wired while the account id comes from the `X-Account-Id` header: it is unauthenticated, so anyone could spend another player's credits, or send a fresh id per request for 10 free credits each time. Sign-in must land first.** Not done: `SPEND.reserve` (waits for budget's cost estimate), a time limit on the pipeline, sign-in. `ArenaOutcome.arena` is still `unknown` (ai's draft; the answer drops `nodes`, `modelCalls` and `refunded`). Tests use `routes/shared/fake-ledgers/FakeLedgers` (budget's real `CreditAccount` behind a fake namespace, recording each call as `reserve:<kind>` so a wrong kind shows even while prices are equal) and each route's `property-tests/` (`pnpm test:properties`).
- **`routes/credits/` is the balance read (budget, 2026-11-19).** `GET /api/credits` with `X-Account-Id` (`CreditStatusRoute`) answers `{balance, dailyAllowance, prices, aiOn, returnsAt?}` from `CREDITS.balance()`, `SPEND.status()`, `CREDIT_PRICES` and `DAILY_CREDITS`. Read-only: it never reserves, settles or refunds (`property-tests/` holds that for any run of reads). 405 `Allow: GET`, 401 without an account. Unauthenticated like the generation routes until sign-in lands.
- `durable-objects/credit-ledger/` and `spend-ledger/` are budget's: AI credits and spend (`docs/cost-and-budget.md`). Each domain has one root file, a Durable Object (`credit-ledger/CreditLedger.ts`, one per account; `spend-ledger/SpendLedger.ts`, the one global), that only wires; the decisions are plain **synchronous** classes beneath it (`credit-ledger/account/CreditAccount.ts`, `spend-ledger/meter/SpendMeter.ts`). Keep them synchronous: the object runs one request at a time, so no `await` between a read and its write is what makes a reserve atomic. Time is passed in as a parameter (only the Durable Object reads the clock). `shared/utc/UtcDay.ts` is shared by both. `spend-ledger/estimate/` holds the tunable `WEAPON_SPEND` (a worst-case reserve and a per-call price) and `SettledWeaponSpend`: an estimate from the outcome's `modelCalls`, since `WeaponOutcome` reports no token usage for the stats stage. `SpendLedger.alarm()` emails the 50/80/100% budget alerts through the `ALERT_MAIL` `send_email` binding (`spend/alerts/`: `SendDueAlerts` marks an alert sent only after its email has gone, so a failure is retried; `email/DeliverAlertEmail` is the untested `cloudflare:email` edge, with its pure builder beneath it; the 100% alert is due once a request is refused for crossing the monthly cap, since spend then stops short of it); `ALERT_TO_ADDRESS` is a secret and, unset, nothing is sent.
- **Fog is the engine's** (`@gunsmith/engine/seat/ViewOfSeat`): the server sends each seat exactly `viewOfSeat(world, seat)`, so a hidden fighter is absent from the frame. Never build a snapshot another way. `TwoBrowsersHidingFromEachOther` reads the received frames to prove it.
- The arena is engine's Duel (`@gunsmith/engine/built-in-arenas/DuelBuiltInArena`) until arenas come from rooms.

## Conventions

- **Decide in plain functions and plain classes; keep the runtime at the edge.** A class is for state (`MatchRoom`) or the Durable Object itself.
- Property tests (`fast-check`, `durable-objects/match/property-tests/**/*Invariants.test.ts`: the room's in `match-room/` with its arbitraries, `step-checks/` and `score-checks/` beneath it, the parser's beside it) are left out of `pnpm checks` and run with `pnpm test:properties`, as the engine's do.
- Tests run in plain node (`vitest.config.ts`): `@cloudflare/vitest-pool-workers` peers on vitest 4 and the workspace is on 5. A route takes a `Request` and an `ApiEnvironment`, so a test passes a fake `MATCHES` namespace.
- Pacing is `durable-objects/match/tick/MatchTick.ts`: a clock 30 times a second plays the engine's 1/60 s steps that real time owes (`StepsOwed`, so a late timer does not slow the game) and sends a snapshot after each. The browser predicts its own fighter and blends the other between snapshots (`webapp/src/online/`), so 30 is enough; at 20 the plain local-feeling game was choppy only because nothing smoothed it. The wire carries `seq` on each input and `ack` (`seq`, `held`) on each snapshot (`@gunsmith/shared/online/types/InputAck`) so the browser knows which of its inputs the server has played.
- Not built yet, on purpose: sign-in (the account id is a header stand-in), D1/Drizzle, the matchmaker, the closing ring and pickup in a room, an "opponent is away" notice for the player who stays, spectators, rate limiting, recordings. Add each when a spec needs it.

## Running

```bash
pnpm api:dev                 # the Worker on :8787 (API_PORT=8790 pnpm api:dev for another port)
pnpm start                   # the webapp; its /api proxy (with WebSockets) points at :8787, or at API_URL
```

For an acceptance run, serve the build with `API_URL=http://localhost:<worker port> pnpm --filter @gunsmith/webapp exec vite preview --port <port> --strictPort`, and point `WEBAPP_URL` at it. Use your own ports and stop only your own servers.
